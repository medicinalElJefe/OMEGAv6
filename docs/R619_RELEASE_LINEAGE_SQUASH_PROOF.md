# R619 — exact production lineage for merge and squash topology

Incident: R617S PR #1145 was merged using squash, producing **one-parent** main commit `891c48166ef495d3d39284261715754b9b31f107`. Its push workflow **did trigger** (run `40279579713`). The `verify` job passed; `deploy-main` failed at `Bind promoted merge lineage` before staging. The previous diagnosis that no production workflow existed was incorrect. R616 remains the last verified production baseline until a newer exact main SHA passes full deployment and authority closure.

R619 preserves two-parent first-parent rollback and second-parent candidate semantics. For one-parent squash it requires a **unique merged PR** associated with the exact promoted SHA, that PR's `base.ref=main` and `base.sha` equal to the sole promoted commit parent, and exact Git tree equality between the PR-head candidate and promoted squash commit. Missing GitHub evidence, mismatched tree, ambiguous PRs, unknown parents, shallow checkout or SHA drift fail closed **before** any production mutation. GitHub API access is read-only; credentials are not emitted. The `deploy-main` job explicitly grants `pull-requests: read` (alongside its existing `contents: read` and `actions: write`), because GitHub's commit-associated PR endpoint requires that permission for a private repository; a unit-test mock cannot establish live token authorization.

This establishes **source lineage**, not candidate CI, Worker promotion, live OMEGA 7 behavior, rollback usability, historical execution or full restoration. All those gates remain independently required. CI covers positive and negative lineage cases; production invokes the binder after exact-main ownership verification and before dependency installation/staging. A new release SHA that includes R617S requires its own full deployment proof. Do not claim the previously failed R617S squash SHA was deployed.

The packaged build receipt now carries a typed `promotion.lineageMode` (`EXACT_TWO_PARENT_MERGE` or `EXACT_SQUASH_PR_AND_TREE`) and the governed release panel shows that mode. The older `GITHUB_MERGE_PARENTS` authority label is retained for compatibility with inherited R200/R372/R496/R517 browser proof contracts; it is **not** sufficient to infer two parents without inspecting `lineageMode`. A missing mode is displayed as `LEGACY_UNTYPED`, not silently converted to a new proof.

The source `rollbackSha` is the **previous main Git commit** for source ancestry, not a promise that this commit was ever deployed or can serve as a rollback target. In particular, R617S is the first parent of a subsequent repair merge but was never deployed. Actual rollback eligibility and the previous live **Cloudflare Worker version** are independently established by `scripts/staged-cloudflare-release.sh` from the live deployment, with its own usability and ownership checks. Do not promote source ancestry to production rollback proof.
