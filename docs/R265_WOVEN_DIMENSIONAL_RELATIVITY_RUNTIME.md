# R265 — Woven Dimensional Relativity Runtime Contract

R265 locks the mature OMEGA interpretation into executable software semantics without freezing unrelated development.

## Canonical composition

R265 treats the previously separate layers as one state-transition system:

1. **Dimensional Relativity** chooses or changes frame, role, representation and active address resolution.
2. **Water Geometry** describes deformation/transport under flow, boundary, pressure, memory, curvature and hysteresis.
3. **Woven Continuity** evaluates whether relational identity/correspondence survives the path.
4. **Violet** is the software transfiguration/re-expression step that asks whether the surviving state can be expressed in the destination skin while preserving future viability and proof context.
5. **Scar/history, orientation and provenance** are carried, never silently reset.
6. **Proof** evaluates explicit residuals when available and never upgrades internal coherence into external empirical truth by assertion.

The runtime operator is:

`FRAME/RESOLUTION/SKIN PARTITION → WATER TRANSPORT → WOVEN PATH/CORRESPONDENCE → VIOLET RE-EXPRESSION → INVARIANT + SCAR + ORIENTATION + PROVENANCE CARRY → RE-CONTEXTUALIZE/REPARTITION → PROVE`

The cycle used by computation, organization and learning is:

`OBSERVE → WATER_TRANSPORT → WOVEN_PATH → VIOLET_REEXPRESSION → PROVE → CARRY → RECONTEXTUALIZE`

## Semantic lock

### Water Geometry

`Shape = Flow × Boundary × Pressure × Memory` remains a state/deformation signature, not a quality score and not a static-shape definition. The runtime separately computes transport coherence and can use the differential Water field only when the required gradients are actually available. Missing gradients remain `NOT_MEASURED`; the runtime does not fabricate them.

### Woven Continuity

Continuity means recoverable relational/path correspondence through transformation. It is not visual similarity, coordinate equality or a requirement that every surface remain unchanged.

### Violet

Violet is a software transfiguration/re-expression contract with future-preservation semantics. R265 deliberately does **not** invent or claim a universal physical Violet equation. A software future-preservation score is identified as software-derived and remains inside the proof boundary.

### Dimensional Relativity

Whole/part, inner/outer, observer, representation and active resolution are frame-relative roles. `12 → 144 → 1,728 → 20,736 → 248,832 → ...` are address/resolution levels unless a separate empirical model independently establishes physical meaning. R265 never converts atlas cardinality into a literal spacetime-dimension claim.

### Orientation

Inverse/outverse orientation is stored separately from structural state. A sign reversal can reverse orientation while preserving the structural metrics. Symmetry and asymmetry remain independent channels rather than complements.

### Scar/history and provenance

Every skin/frame transition carries scar/history and declared provenance. Returned/observed, derived and inferred values must remain distinguishable. A new skin is allowed; silent history erasure is not.

## Healthy promotion rule

R265 is a **cross-skin integrity contract**, not a new promotion authority.

A capability is not blocked because it is new. A skin is not blocked because it is new. Healthy development may advance when the invariant contract is preserved, or when an intentional version migration is declared and re-proved through the already-established release path.

R265 may emit residual pressure or request review from an existing gate, but `blockedByR265` is false by design. Source mutation/promotion remains R240, dispatch remains R147, exact return proof remains R141, durable history remains R146, CanonState admission remains R125, and `.github/workflows/ci.yml` remains the sole canonical production writer.

## Applied skins

- `FUNCTION` — preserve declared inputs/outputs, invariants and residuals.
- `COMPUTE` — execute the combined Water/Woven/Violet/frame envelope.
- `ORGANIZE` — partition/repartition by dependency, frame and active resolution.
- `LEARN` — update only from explicit outcomes or observed transitions; unchosen candidates are not failures.
- `RENDER` — produce lawful projections without mutating evidence or CanonState.
- `EXECUTE` — keep execution receipts separate from scientific truth and promotion.
- `SELF_BUILD` — use R265 for planning/evaluation while R240 remains the single source-mutation/promotion authority.
- `EVIDENCE` — preserve observed/returned/derived/inferred evidence classes.

## Proof requirements

R265 distinguishes computation from proof:

- A round-trip proof is `NOT_MEASURED` unless an actual round-trip residual is supplied.
- A commuting-transform proof is `NOT_MEASURED` unless an actual commutation residual is supplied.
- A failed measured residual requests review by existing gates; it does not secretly create a new release authority.
- Internal computation coherence is an operational metric, not external scientific validation.
- Local learning may change retrieval memory, proof priors or explicit outcome memory; foundation-model weights must not be claimed as changed unless actual weight-training proof exists.

## Why this is a lock without a freeze

The semantic invariants are locked. Implementations are not.

Future renderers, solvers, training systems, data sources, skins, models and execution adapters may replace or extend current implementations as long as they either preserve the R265 invariant contract or explicitly version the changed semantics and re-prove the migration. This makes the framework stable enough not to be misunderstood while leaving OMEGA free to continue healthy promotion and capability growth.
